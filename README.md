On Apple M2 the cost per element read rises from 0.17 ns at stride 1 to 2.53 ns at stride 16 (one element per 128-byte cache line), a 14.5x increase, and is 3.28 ns at stride 128, so a strided traversal wastes most of every fetched line and is limited by memory rather than arithmetic. Interchanging the dense kernel from i-j-k to i-k-j (N=1024, M=512, c backend) turns the stride-N walk over B into stride-1 accesses and gives a 2.73x speedup with bit-identical results. With 128-byte lines, counters packed on one line take 0.014 s at P=4 versus 0.008 s when padded to one line each (1.8x slower; T(P)/T(1) = 2.4 unpadded vs 1.4 padded for equal work per worker), while privatization takes 0.008 s. Karp-Flatt e(4) is 2.88 unpadded vs 1.50 padded by the handout formula (0.47 vs 0.13 with work-normalised speedup), diagnosing cache-line ping-pong as the unpadded bottleneck. The increment loop of this run executes in compiled C via ctypes because CPython's per-iteration overhead masked most of the contention in a pure-Python run. Rows with P above the performance-core count may include slower efficiency cores, so the cleanest comparison is at small P. The stencil's strong scaling is poor: the Amdahl fit gives an effective serial fraction s = 1.03 (S_max = 1.0x), with 12% efficiency at P=8, versus 19% weak-scaling efficiency at P=8 (Gustafson g = 0.90); the effective s lumps true serial work with barrier cost and memory-bandwidth saturation. Its arithmetic intensity is 0.167 FLOP/byte, well below the ridge point of 2.2 FLOP/byte, so the kernel is memory-bandwidth bound (peak GFLOP/s 220.0 and bandwidth 100 GB/s are estimates: user supplied; user supplied theoretical peak). This CPU reports no L3 cache, so no L3 comparison is made.
